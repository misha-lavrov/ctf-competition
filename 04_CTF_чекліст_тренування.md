# CTF — чекліст тренування задач

> Версія: 1.0  
> Оновлено: 6 вересня 2026  
> Ціль: пройти короткий, різноплановий маршрут до Чемпіонату Вінницької області з CTF

## Як користуватися

1. Обери **один** основний маршрут: picoCTF або CTFlearn. Не треба проходити обидва.
2. На одну задачу дай собі 10–15 хвилин чесної спроби; лише потім бери hint або став точне запитання.
3. Після кожної задачі заповни короткий коментар. Важливо не просто здати flag, а зрозуміти патерн.
4. Якщо назву picoCTF-задачі не знаходить пошук — пропусти її та бери наступну того самого напряму.

Позначки: `[ ]` — не почато, `[x]` — пройдено.  
Статус у коментарі: `сам`, `з hint`, `із розбором`, `відкладено`.

### [ Х ] 2. MY GIT

- Напрям: General Skills / Git
- Орієнтир: README, локальні `git config user.name` і `user.email`, commit metadata
- Час: 10–20 хв
- Мета: зрозуміти, чому ім'я та email автора коміту — не доказ особи.

**Коментар після задачі**

```text
Статус: DONE
Час: 5хв
Яку вимогу знайшов у README: 
Only flag.txt pushed by ```root:root@picoctf``` will be updated with the flag.

Які Git-команди використав:
git config user.name "root"
git config user.email "root@picoctf"
touch flag.txt
git add .
git commit -m "added flag"
git push

Security-висновок: 
user.name та user.email — це лише metadata коміту, які кожен може локально змінити.
Вони не є автентифікацією і не доводять, що коміт справді створив root.
Сервер задачі помилково довіряв цим полям.

Питання або коментар:
```

### [ X ] 6. GET aHEAD

- Напрям: Web / HTTP
- Орієнтир: HTTP-методи, `curl -I`, response headers
- Час: 10–20 хв
- Мета: побачити, що різні HTTP-методи можуть давати різну поведінку сервера.

**Коментар після задачі**

```text
Статус: DONE
Час:
Які HTTP-методи перевірив:
HEAD — через curl -I.

Що змінилося у відповіді сервера:
Сервер повернув flag у власному HTTP-заголовку `flag`.
Тіло відповіді не завантажувалось, бо HEAD повертає лише headers.

Ключова ідея:
HTTP має не лише GET і POST, а й HEAD, PUT, DELETE, OPTIONS тощо.
Різні методи можуть викликати різну поведінку сервера.
У Web-задачах варто перевіряти HTTP headers через curl -I,

DevTools Network або Burp Suite.
Питання або коментар:
```

### [ Х ] 7. Cookies

- Напрям: Web
- Орієнтир: browser cookies, DevTools → Application/Storage
- Час: 10–20 хв
- Мета: зрозуміти, які дані клієнт може змінювати і чому сервер має їх перевіряти.

**Коментар після задачі**

```text
Статус: DONE
Час:
Який cookie / параметр був важливий:
Cookie `name`. Спочатку сайт встановив `name=0`.
Я вручну змінив його до `name=18`, після чого сервер показав flag.

Де його переглянув або змінив:
Chrome DevTools (F12) → Application → Storage → Cookies →
http://wily-courier.picoctf.net:53907/
Також у Network → Headers було видно, що браузер надсилає:
Cookie: name=<значення>

Ключова ідея:
Cookie зберігається на стороні клієнта. Користувач може змінити його
через DevTools, curl або Burp Suite. Сервер не має сприймати його
значення як гарантовано правдиве.

Чому така перевірка небезпечна для реального сервісу:
Якщо сервер визначає за cookie роль, user ID, ціну товару, знижку або
доступ до приватних даних, користувач може підмінити значення й отримати
чужі дані або більші права.

Як треба робити правильно:
Cookie має містити лише випадковий session token, а сервер уже на своїй
стороні зберігає, кому належить сесія та які в людини права.
На кожен запит сервер перевіряє автентифікацію й авторизацію.
```
