## Крок 0. Підготовка — доступ до файлу з WSL

Файл лежав у Windows за шляхом `C:\Users\...\Downloads\FlagEater.zip`. У WSL диски Windows підключені під `/mnt/c/...`, тому спочатку створюємо робочу теку і копіюємо файл у "рідну" файлову систему Linux (працювати з файлами там швидше і без проблем зі спецсимволами в шляхах):

```bash
mkdir -p ~/ctf/flageater
cp "/mnt/c/Users/.../Downloads/FlagEater.zip" ~/ctf/flageater/FlagEater.zip
cd ~/ctf/flageater
```

## Крок 1. Розпакування та перше знайомство з файлами

```bash
unzip -l FlagEater.zip      # подивитись зміст архіву, не розпаковуючи
unzip FlagEater.zip         # розпакувати
file FlagEater 6925431671.bin
chmod +x FlagEater           # дати файлу права на виконання
```

**`file`** — визначає тип файлу за вмістом (сигнатурою), а не за розширенням. Показав, що `FlagEater` — це **ELF 64-bit PIE executable, stripped**:
- **ELF** — формат виконуваних файлів у Linux (аналог `.exe` у Windows).
- **PIE** (Position Independent Executable) — код може завантажуватись у пам'ять за будь-якою адресою (стандартний сучасний захист).
- **stripped** — з файлу видалено таблицю символів (імена функцій/змінних), що ускладнює реверс.

`6925431671.bin` — просто "data", 28 байт (це і є зашифрований прапор).

## Крок 2. Пошук текстових підказок

```bash
strings -n 6 FlagEater > strings.txt     # усі "читабельні" рядки довжиною від 6 символів
grep -iE "flag|xor|aes|key|error|usage" strings.txt
```

**`strings`** — виводить усі послідовності друкованих символів у бінарному файлі. Часто в них лишаються шляхи, повідомлення про помилки, назви функцій тощо.

У нашому випадку прямих підказок про алгоритм не знайшлось — довелось копати глибше.

## Крок 3. Спостереження за поведінкою програми

```bash
./FlagEater
```

Вивело `no flag.txt` — програма шукає файл `flag.txt` у поточній теці. Це дало ідею для **диференціального аналізу**: підсунути програмі власний тестовий файл із відомим вмістом і подивитись, як він перетвориться.

```bash
python3 -c "open('flag.txt','wb').write(b'A'*28)"   # тестовий файл: 28 байт 'A'
./FlagEater
ls -la *.bin
```

Кожен запуск створював **новий** `.bin`-файл із новим числом у назві, і **шифротекст щоразу був різний** — отже, ключ не сталий, а якось залежить від часу/випадковості.

## Крок 4. Перевірка імпортованих функцій (`objdump`)

```bash
objdump -T FlagEater | grep -iE "rand|time|crypt|getpid"
ldd FlagEater
```

**`objdump -T`** — показує таблицю **динамічних символів**: які зовнішні функції (з бібліотек типу `libc`) бінарник використовує. Навіть у stripped-файлі ці імена лишаються, бо потрібні під час запуску.

**`ldd`** — показує, які спільні бібліотеки (`.so`) підвантажує програма.

У `FlagEater` (зовнішній шар) знайшли `time`, `getpid`, `system` — і купу C++ функцій роботи з рядками (`ostringstream`, `basic_string` тощо), але **не було** `rand`/`srand`. Це виявилось важливим сигналом.

## Крок 5. Дизасемблювання через radare2

```bash
r2 -q -A -c 'afl' FlagEater > funcs.txt      # список знайдених функцій
r2 -q -A -c 'pdf @ main' FlagEater > main_asm.txt   # дизасемблювання функції main
```

**radare2 (`r2`)** — безкоштовний дизасемблер/фреймворк для реверс-інжинірингу.
- `-A` — виконати автоматичний аналіз коду при завантаженні (шукає функції, перехресні посилання тощо). **Важливо:** аналіз і команда виводу мають бути в **одному** запуску `r2` — інакше результати аналізу губляться.
- `afl` (**a**nalyze **f**unctions **l**ist) — список знайдених функцій.
- `pdf @ main` (**p**rint **d**isassembly of **f**unction) — дизасемблювати конкретну функцію.

**Що виявили:** `main` у `FlagEater` містить величезний блок "сміттєвих" даних (14704 байт), який у циклі розшифровується через `XOR 0x5a` (просте додавання по модулю 2 з константою) і записується у файл, після чого програма робить:

```
chmod +x '<тимчасовий файл>' && '<тимчасовий файл>' && rm -f '<тимчасовий файл>'
```

тобто `FlagEater` — це **dropper** ("скидач"): він розпаковує **другий, справжній** бінарник, записує його на диск, запускає і одразу видаляє. Саме той другий бінарник і шифрує `flag.txt`.

## Крок 6. Витяг вбудованого бінарника без його запуску

Замість того, щоб намагатись "зловити" тимчасовий файл під час миттєвого виконання, статично витягли блок даних прямо з `FlagEater`:

```bash
r2 -q -c 's 0x3060; wtf blob.raw 0x3970' FlagEater   # зберегти 0x3970 байт з адреси 0x3060 у файл
python3 -c "
data = open('blob.raw','rb').read()
dec = bytes(b ^ 0x5a for b in data)     # розшифрувати XOR-ом
open('payload.elf','wb').write(dec)
"
file payload.elf       # переконатись, що вийшов валідний ELF
chmod +x payload.elf
```

**`s <адреса>`** у radare2 — перейти ("seek") на вказану адресу.
**`wtf <файл> <розмір>`** (**w**rite **t**o **f**ile) — зберегти вказану кількість байт поточної позиції у зовнішній файл.

Отримали другий бінарник — саме він містить логіку шифрування прапора.

## Крок 7. Аналіз "справжнього" шифрувальника (`payload.elf`)

Повторили розвідку на новому файлі:

```bash
objdump -T payload.elf | grep -iE "rand|srand|time"
strings -n 6 payload.elf | grep -iE "flag"
```

Цього разу знайшли **`rand`, `srand`, `time`** — класична схема:

```
seed = time(NULL);      // поточний час у секундах
srand(seed);             // ініціалізація генератора псевдовипадкових чисел
for (i = 0; i < довжина_прапора; i++) {
    key_byte = rand();          // наступне псевдовипадкове число
    зашифрований[i] = прапор[i] XOR (key_byte & 0xFF);   // XOR з молодшим байтом
}
```

Це підтвердили дизасемблюванням (`r2 -q -A -c 'pdf @ main' payload.elf`) — побачили виклики `call sym.imp.time`, `call sym.imp.srand`, і в циклі `call sym.imp.rand` та інструкцію `xor byte [rax], dl`.

## Крок 8. Емпірична перевірка формули (LD_PRELOAD-хук)

Дизасемблер дає гіпотезу, але легко помилитись у деталях (наприклад, яке саме значення використовується для назви файлу). Тому написали малу C-бібліотеку, яка **перехоплює** виклики `time`, `srand`, `rand` і друкує їхні реальні аргументи/результати під час фактичного виконання програми:

```bash
cat > hook.c << 'EOF'
#define _GNU_SOURCE
#include <stdio.h>
#include <dlfcn.h>
#include <time.h>
#include <stdlib.h>

time_t time(time_t *t) {
    static time_t (*real_time)(time_t*) = NULL;
    if (!real_time) real_time = dlsym(RTLD_NEXT, "time");
    time_t r = real_time(t);
    fprintf(stderr, "[HOOK] time() = %ld\n", (long)r);
    return r;
}
void srand(unsigned int seed) {
    static void (*real_srand)(unsigned int) = NULL;
    if (!real_srand) real_srand = dlsym(RTLD_NEXT, "srand");
    fprintf(stderr, "[HOOK] srand(seed=%u)\n", seed);
    real_srand(seed);
}
int rand(void) {
    static int (*real_rand)(void) = NULL;
    if (!real_rand) real_rand = dlsym(RTLD_NEXT, "rand");
    int r = real_rand();
    fprintf(stderr, "[HOOK] rand() = %d\n", r);
    return r;
}
EOF
gcc -shared -fPIC -o hook.so hook.c -ldl
LD_PRELOAD=./hook.so ./payload.elf 2> hook_out.txt
```

**Що таке `LD_PRELOAD`:** змінна середовища Linux, яка каже завантажувачу підключити вказану бібліотеку **першою**, перед стандартними. Якщо в ній є функція з тією самою назвою (наприклад, `rand`), вона "перекриє" оригінальну — весь код програми буде викликати нашу версію замість справжньої з `libc`. Дуже зручний спосіб "підслухати" виклики бібліотечних функцій без зміни самої програми.

**`dlsym(RTLD_NEXT, "ім'я")`** — попри перехоплення, дає доступ до **справжньої** оригінальної функції, щоб можна було її викликати і не зламати роботу програми.

**Результат:** на тестовому `flag.txt` = 28×`'A'` побачили реальні числа (`time() = 1789737492`, і 28 значень `rand()`). Перевірили в Python:

```python
keystream = bytes(r & 0xFF for r in rand_values)
decoded   = bytes(c ^ k for c, k in zip(ciphertext, keystream))
# decoded == b'AAAA...A'  →  формула підтверджена на 100%
```

## Крок 9. Підбір (brute-force) seed для реального прапора

Для власного тестового запуску ми знаємо `seed` напряму (з хука). Але для **реального** `6925431671.bin` ми seed не знаємо — програма, яка його створила, вже видалена (dropper сам себе прибирає). Проте ми знаємо **приблизний час**, коли адмін генерував завдання — з дати файлу в архіві (`2025-10-25 01:35`).

Ідея: **перебрати** (brute-force) усі можливі значення `time()` у вузькому вікні навколо цієї дати, і для кожного перевірити — чи дає воно дешифрований текст, що починається з `cyberunittech{`.

```c
// brute.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main() {
    unsigned char ct[28] = { /* байти з 6925431671.bin */ };
    long start = 1761269700; // Oct 24 2025 01:35 UTC (-1 день)
    long end   = 1761442500; // Oct 26 2025 01:35 UTC (+1 день)
    unsigned char buf[29];
    for (long seed = start; seed <= end; seed++) {
        srand((unsigned int)seed);
        for (int i = 0; i < 28; i++) {
            int r = rand();
            buf[i] = ct[i] ^ (unsigned char)(r & 0xFF);
        }
        buf[28] = 0;
        if (memcmp(buf, "cyberunittech{", 14) == 0)
            printf("FOUND seed=%ld flag=%s\n", seed, buf);
    }
    return 0;
}
```

```bash
gcc -O2 -o brute brute.c
./brute
```

**Чому це швидко:** перебір навіть кількох діб (сотні тисяч секунд) — це лише сотні тисяч ітерацій, кожна з яких — 28 викликів `rand()`. Для C-програми це частки секунди.

**Важливо:** `rand()`/`srand()` мають бути з тієї ж бібліотеки (`glibc`), що й на машині, де компілювався оригінальний `payload.elf` — інакше послідовність псевдовипадкових чисел буде іншою. Тому весь перебір робимо **локально в тому самому WSL**, а не в сторонньому середовищі.

## Загальні висновки / чого повчитись на майбутнє

1. **`file` + `strings`** — завжди перший крок для будь-якого невідомого бінарника.
2. **`objdump -T` / `ldd`** — навіть у stripped-бінарнику видно, які бібліотечні функції він використовує; це вже підказка про логіку (`rand`/`srand`/`time` → псевдовипадковий XOR-шифр).
3. **Диференціальний аналіз** (підсунути відомі вхідні дані й подивитись на вихід) — часто швидший шлях, ніж повний дизасемблер "з нуля".
4. **radare2** — базовий інструмент: `-A` для аналізу, `afl` для списку функцій, `pdf @ <функція>` для дизасемблювання, `wtf` для витягання сирих байтів з файлу.
5. **Дроппери** (програма в програмі) — типовий прийом і в CTF, і в реальному шкідливому ПЗ: варто перевіряти, чи не "ховає" бінарник ще один усередині (великі блоки однотипних даних, XOR-цикли за адресою в `.rodata`/`.data`).
6. **`LD_PRELOAD`-хуки** — надійний спосіб перевірити гіпотезу про поведінку програми, коли не довіряєш власному прочитанню асемблера (а довіряти сліпо не варто — ми самі один раз неправильно прочитали, яке значення йде в назву файлу).
7. Коли ключ шифрування залежить від **часу запуску**, а час відомий хоча б приблизно (наприклад, з дати файлу) — це майже завжди означає **brute-force вузького вікна** секунд, а не намагання вгадати точну секунду.
