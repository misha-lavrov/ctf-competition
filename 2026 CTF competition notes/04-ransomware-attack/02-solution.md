## Крок 0. Підготовка середовища

### Встановити WSL (один раз на Windows)

WSL = "Linux всередині Windows". Потрібен, бо всі forensics-інструменти — під Linux.

```powershell
wsl --install
```
Після цього перезавантажити компʼютер і завести користувача Ubuntu.
Детально: https://learn.microsoft.com/en-us/windows/wsl/install

### Розпакувати архів із завданням

Архів лежав у `C:\ransomware_attack.zip`. У Windows диск `C:` доступний з WSL
через `/mnt/c/`.

```bash
mkdir -p ~/ransomware_attack && cd ~/ransomware_attack
cp /mnt/c/ransomware_attack.zip .   # cp = copy, копіюємо файл
unzip ransomware_attack.zip          # unzip = розпакувати zip
ls -la                               # ls -la = показати всі файли з деталями
```

Після цього маємо `memory_dump.raw` і `top_secret_recover_at_all_cost.txt.enc`.

### Встановити Volatility 3 (головний інструмент для аналізу памʼяті)

**Volatility** — це "швейцарський ніж" для аналізу дампів памʼяті. Уміє діставати
список процесів, мережеві зʼєднання, завантажені бібліотеки тощо.

```bash
sudo apt install -y python3-pip           # менеджер пакетів Python
pip3 install volatility3 --break-system-packages
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc   # додаємо vol у PATH
source ~/.bashrc                          # перечитуємо налаштування
vol -h                                    # перевірка, що працює
```

> Команда називається `vol` (не `vol3`). Загальний вигляд:
> `vol -f <файл_дампу> <плагін>`

## Підзадачі 3, 4, 5, 6: процес вірусу — ✅ всі

*(робимо разом, бо все з одного плагіна)*

Плагін `windows.pslist` = список усіх процесів, що працювали в момент знімку
(як диспетчер задач).

```bash
vol -f memory_dump.raw windows.pslist
```

У кінці списку видно підозрілі процеси:
```
PID   PPID  ImageFileName    Offset(V)
100   5192  c7f_3ncrYp7.ex   0xa787a81b5080   ← сам вірус
1136  5496  go-winpmem_amd   ...              ← інструмент дампу памʼяті
```

- **Підзадача 4** (назва вірусу): `c7f_3ncrYp7.exe` → `UR{c7f_3ncrYp7.exe}`
- **Підзадача 5** (адреса процесу): колонка `Offset(V)` → `UR{0xa787a81b5080}`
- **Підзадача 6** (хто запустив): колонка `PPID` (Parent PID) = `5192`.
  Дивимось, що це за процес → `powershell.exe`. → `UR{5192}`
- **Підзадача 3** (інструмент дампу): процес `go-winpmem_amd64...` → це **WinPmem**.
  → `UR{winpmem}`

> **PID** = Process ID (номер процесу). **PPID** = Parent PID (номер процесу,
> який його запустив). Ланцюжок тут: powershell (5192) запустив вірус (100).

Щоб побачити повні командні рядки процесів (з якими аргументами запускались):
```bash
vol -f memory_dump.raw windows.cmdline
```
Тут видно шлях вірусу: `C:\Users\Administrator\Downloads\c7f_3ncrYp7.exe`

## Підзадача 8: Захований hex-прапор у вірусі — ✅

Спочатку **дістаємо сам файл вірусу з памʼяті** (він же стерся з диска, тож беремо
з дампу). Знаходимо його адреси через `filescan`, тоді витягуємо через `dumpfiles`.

```bash
mkdir -p dumped
# знайти файл вірусу в памʼяті:
vol -f memory_dump.raw windows.filescan | grep -i "c7f_3ncrYp7"
# витягнути його (--pid 100 --dump зберігає образ процесу):
vol -f memory_dump.raw -o dumped windows.pslist --pid 100 --dump
```
`-o dumped` = куди зберегти результат.

Тепер шукаємо в цьому файлі довгі hex-рядки (прапор захований як hex-текст):

```bash
cd dumped
strings 100.c7f_3ncrYp7.ex.*.dmp | grep -oE "([0-9a-fA-F]{2}){8,}"
```
`grep -oE "..."` = вивести тільки збіги за регулярним виразом;
`([0-9a-fA-F]{2}){8,}` = "мінімум 8 пар hex-символів підряд".

Серед результатів — рядок:
```
55527B54316D335F4630725F35306D335F523376337235335F336E67316E333372316E677D0A
```
Він починається на `5552` = `UR` в ASCII. Розкодовуємо hex у текст:

```bash
echo "55527B54316D335F4630725F35306D335F523376337235335F336E67316E333372316E677D0A" | xxd -r -p
```
`xxd -r -p` = перетворити hex назад у звичайні байти (текст).

Результат: `UR{T1m3_F0r_50m3_R3v3r53_3ng1n33r1ng}`

**Відповідь:** `UR{T1m3_F0r_50m3_R3v3r53_3ng1n33r1ng}`

## Підзадача 9: XOR-маска — ✅ (підтверджено платформою)

XOR — проста математична операція, якою часто "легко" шифрують дані. Щоб знайти
маску, треба глянути в код вірусу — використовуємо **radare2** (інструмент для
зворотної розробки / дизасемблювання).

```bash
sudo apt install -y radare2
r2 -A file.0xa787a6da80c0.*.img   # -A = автоматично проаналізувати
```

Усередині radare2 шукаємо XOR-інструкції з константою:
```
/ad xor        # знайти всі інструкції xor у коді
```

Серед сотень результатів (переважна більшість — "шум": фрагменти рядків і
даних, які дизасемблер помилково прочитав як код) виділяється один рядок:
`xor cl, 0xaa`. `0xAA` (двійкове 10101010) — типова "кругла" константа, якою
навчальні задачі часто позначають XOR-маску. Вихід із radare2: `q`.

> **Чесно про метод:** цю відповідь спершу знайшли **евристикою**, а не строгим
> підтвердженням із коду — `0xAA` просто виділявся на тлі шуму (єдина
> однобайтова XOR-константа, не 0x00 і не типовий `xor eax,eax` для обнулення).
> Платформа підтвердила відповідь як правильну з першої спроби, тож здогадка
> виявилась вірною. Але це **не надійний метод** для наступного разу: краще
> знайти саму функцію шифрування через xref (`axt`) на рядок помилки поруч і
> подивитись код безпосередньо, а не покладатись на візуальний збіг у
> зашумленому виводі `/ad xor` по всьому бінарнику.

**Відповідь:** `UR{0xaa}`

## Підзадача 10: AES-ключ шифрування — ✅

Ключ згенеровано випадково (через `BCryptGenRandom`), тож у самому файлі вірусу
його немає — він живе тільки в **памʼяті** під час роботи. Для пошуку AES-ключів
у дампі памʼяті є спеціальний інструмент **aeskeyfind**: він упізнає ключі за
математичною структурою "розкладу ключа" (key schedule) AES.

```bash
sudo apt install -y aeskeyfind
aeskeyfind memory_dump.raw
```

Інструмент видає багато кандидатів. **Головна ознака справжнього ключа — він
повторюється в списку найчастіше** (у нас — 12+ разів проти 1–2 у "шуму"):

```
a7f34b1d9c8257e13eb2d86f11a4c97d54890733afe61ac3de0f62954cb7203a
```
Це рівно 64 hex-символи = **32 байти** (AES-256), що збігається з підказкою у
вірусі "Key length should be 32 bytes".

Перші 8 байт: `a7 f3 4b 1d 9c 82 57 e1`

**Відповідь:** `UR{0xA7,0xF3,0x4B,0x1D,0x9C,0x82,0x57,0xE1}`

## Підзадача 11: Розшифровка файлу — ⏳ не завершено (доробити самостійно)

Маємо все: AES-ключ (32 байти) і, можливо, XOR-маску 0xAA як "перший рівень".
Пишемо Python-скрипт, який пробує варіанти розшифровки.

> **Статус:** цей крок у проходженні лишився незавершеним — скрипт написаний, але
> результат його виконання не був зафіксований (чат перервався на новій задачі).
> Нижче — план, як довести до кінця самостійно.

```bash
pip3 install pycryptodome --break-system-packages   # бібліотека для AES
```

```python
# decrypt.py
from Crypto.Cipher import AES
from Crypto.Util.Padding import unpad

key = bytes.fromhex("a7f34b1d9c8257e13eb2d86f11a4c97d54890733afe61ac3de0f62954cb7203a")
data = open('top_secret_recover_at_all_cost.txt.enc', 'rb').read()

def try_decrypt(label, blob):
    iv, ct = blob[:16], blob[16:]     # перші 16 байт = IV (вектор ініціалізації)
    try:
        pt = AES.new(key, AES.MODE_CBC, iv).decrypt(ct)
        print(f"[{label}] {unpad(pt, 16)}")
    except Exception as e:
        print(f"[{label}] failed: {e}")

try_decrypt("plain AES-CBC", data)                       # варіант 1: тільки AES
try_decrypt("XOR-then-AES", bytes(b ^ 0xAA for b in data))  # варіант 2: XOR потім AES
```

```bash
python3 decrypt.py
```

Той варіант, що дасть читабельний текст із `UR{...}` — і є фінальна відповідь.

> **Що таке IV:** AES у режимі CBC потребує "вектор ініціалізації" (16
> випадкових байтів). Його зазвичай кладуть на початок зашифрованого файлу —
> тому беремо перші 16 байт як IV, а решту як шифротекст.

### Що доробити самостійно

Якщо `plain AES-CBC` і `XOR-then-AES` не дадуть читабельного тексту, спробуй по
черзі ще кілька комбінацій — це нормальна практика при реверсі невідомої схеми
шифрування:

1. **AES-потім-XOR** (порядок операцій міг бути зворотний):
   ```python
   pt = AES.new(key, AES.MODE_CBC, iv).decrypt(ct)
   result = bytes(b ^ 0xAA for b in pt)
   ```
2. **Інший режим AES**, якщо CBC не підійде — спробуй `AES.MODE_ECB` (без IV
   узагалі, шифротекст ділиться на блоки по 16 байт) або `AES.MODE_CTR`.
3. **IV не на початку файлу** — якщо результат виходить "майже правильний", але
   збитий перший блок (16 байт), значить IV, можливо, нульовий
   (`iv = b'\x00' * 16`) або зашитий десь в іншому місці памʼяті — тоді весь
   `data` (усі 144 байти) — це чистий шифротекст без IV попереду.
4. **Перевір, чи то взагалі увесь ключ.** У задачі 10 ми брали ключ, що
   найчастіше повторювався в `aeskeyfind`. Якщо жоден варіант не спрацює —
   варто перевірити 2-3 наступні за частотою кандидати з того самого списку.

Найнадійніший спосіб знайти правильну комбінацію без перебору навмання — знайти
в коді вірусу (через `radare2`) саму функцію розшифровки/шифрування і прочитати
послідовність викликів: спершу XOR чи спершу AES, який режим, звідки береться IV.

## Загальні уроки з цієї задачі

1. **Memory forensics** = усі секрети працюючої програми (ключі, паролі,
   розкодовані рядки) лежать у RAM у відкритому вигляді. Дамп памʼяті — це
   скарбниця.
2. **Volatility 3** — базовий інструмент: `windows.info`, `windows.pslist`,
   `windows.cmdline`, `windows.netscan`, `windows.dlllist`, `windows.dumpfiles`.
3. **strings + grep** — швидко знайти текст/URL/hex у будь-якому бінарному файлі.
4. **radare2** — коли треба зазирнути в сам код програми.
5. **aeskeyfind** — спеціалізований пошук AES-ключів у дампі памʼяті; справжній
   ключ повторюється найчастіше.
6. **Порада щодо роботи в терміналі:** не вставляй назад у консоль весь
   попередній вивід — копіюй тільки саму команду. Інакше bash намагається
   виконати кожен рядок як команду і сиплються помилки.
