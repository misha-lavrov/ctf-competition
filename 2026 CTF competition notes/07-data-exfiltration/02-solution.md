# Задача 7: Simple Data Exfiltration Detection — рішення покроково

Робота велась у WSL (Windows Subsystem for Linux) на CTF-стенді. Нижче — повний хід рішення з поясненням кожної нової команди/утиліти.

## Крок 0. Підготовка середовища

Файл лежав на Windows-диску (`C:\Users\...\Downloads\...`). У WSL диски Windows підмонтовані під `/mnt/c/...`, тому файл спершу скопійовано у "рідну" файлову систему Linux (це швидше і надійніше для роботи з утилітами):

```bash
mkdir -p ~/ctf/exfil
cp "/mnt/c/Users/.../Downloads/Simple Data Exfiltration Detection.pcap" ~/ctf/exfil/exfil.pcap
cd ~/ctf/exfil
file exfil.pcap
```

- `file exfil.pcap` — визначає реальний тип файлу за вмістом (а не за розширенням). Показало `pcapng capture file` — це сучасний формат захоплення трафіку (наступник простого `.pcap`), який читають ті самі інструменти.

Встановлено набір інструментів для аналізу трафіку:

```bash
sudo apt update
sudo apt install -y wireshark tshark tcpdump ngrep binwalk foremost
```

Коротко, що це за інструменти:
- **wireshark** — графічний аналізатор трафіку (переглядає `.pcap`, розбирає протоколи, показує все "по-людськи").
- **tshark** — та сама "начинка" Wireshark, але консольна утиліта. Зручна для скриптів і фільтрації великих файлів без GUI — основний інструмент цього завдання.
- **tcpdump** — консольна утиліта для захоплення/читання трафіку (тут не знадобилась, бо трафік уже захоплений у файл).
- **ngrep** — пошук текстових патернів у мережевих пакетах (аналог `grep`, але для трафіку).
- **binwalk**, **foremost** — утиліти для пошуку "прихованих" файлів усередині бінарних даних (аналіз вбудованих файлів/сигнатур). У цьому завданні не знадобились — вони більше для інших типів forensics-задач (напр. коли файл прихований всередині іншого файлу).

## Task 1: IP-адреса сервера ексфільтрації

**Мета:** знайти зовнішню IP-адресу, куди йдуть вкрадені дані.

Спочатку — загальний огляд, що взагалі є в дампі:

```bash
tshark -r exfil.pcap -q -z io,phs
```

- `-r file` — читати файл замість live-захоплення.
- `-q` — не виводити кожен пакет, а тільки підсумок (тихий режим).
- `-z io,phs` — статистика "Protocol Hierarchy" (ієрархія протоколів): скільки трафіку припадає на кожен протокол (ARP, DNS, TCP, TLS...). Дає загальну картину: "з чого складається" дамп.

Далі — хто з ким і скільки спілкувався:

```bash
tshark -r exfil.pcap -q -z conv,ip     # розмови по IP
tshark -r exfil.pcap -q -z conv,udp    # розмови по UDP (з портами)
```

`-z conv,ip` / `conv,udp` — статистика "Conversations": список пар адрес (host A <-> host B), скільки пакетів/байтів в кожну сторону.

**Що знайдено:** серед звичайних DNS-розмов (`хост <-> 192.168.65.7:53`, локальний DNS-резолвер, з нормальними запит→відповідь) виділялась група розмов `172.16.1.5 <-> 22.50.109.94:53` — 14 окремих "сесій", кожна рівно 1 пакет / 105 байт, **тільки в один бік** (без жодної відповіді). Це нетипово для реального DNS: справжній сервер завжди відповідає. Односторонній "DNS-подібний" трафік на нестандартний зовнішній IP, що повторюється регулярно — класична ознака DNS-ексфільтрації.

**Прапор:** `UR{22.50.109.94}`

## Task 2: Виробник зараженого пристрою за MAC-адресою

**Мета:** визначити виробника мережевої карти хоста `172.16.1.5` (джерела ексфільтрації).

Дамп записаний у форматі "Linux cooked capture" (`sll`) — це буває, коли захоплення велось не на конкретному Ethernet-інтерфейсі, а "з усіх інтерфейсів" (`any`). Через це MAC-адреса лежить не в стандартному полі `eth.src`, а в `sll.src.eth`.

Спочатку перевірено, які поля взагалі є в `sll`-шарі:

```bash
tshark -G fields | grep -i sll
```

- `-G fields` — вивантажує повний список усіх полів, які tshark вміє розпізнавати (свого роду довідник). У поєднанні з `grep` — пошук потрібної групи полів.

Потім витягнуто саму MAC-адресу:

```bash
tshark -r exfil.pcap -Y "ip.src==172.16.1.5" -T fields -e sll.src.eth
```

- `-Y "..."` — display filter (фільтр за умовою, той самий синтаксис, що і в GUI Wireshark).
- `-T fields -e <поле>` — вивести не весь пакет, а тільки значення конкретного поля (можна кілька `-e`).

Результат: `90:4c:81:b6:03:24` (однакова для всіх пакетів — це один і той самий хост).

Найпростіший спосіб дізнатись виробника — подивитись повний розбір одного пакета: Wireshark сам матчить перші 3 байти MAC (OUI, Organizationally Unique Identifier) проти вбудованої бази виробників IEEE:

```bash
tshark -r exfil.pcap -Y "ip.src==172.16.1.5" -V | head -40
```

- `-V` — "verbose": повний, розгорнутий розбір пакета по шарах (як у GUI-панелі Wireshark), а не одним рядком.

У виводі одразу видно: `Source: HewlettPacka_b6:03:24 (90:4c:81:b6:03:24)` — тобто OUI `90:4c:81` належить Hewlett-Packard.

*(Альтернативний спосіб, якщо потрібне лише ім'я виробника без ручного читання `-V`: пошук OUI у локальній базі `/usr/share/wireshark/manuf`, напр. `grep -i "^90:4C:81" /usr/share/wireshark/manuf`, або будь-який онлайн OUI-lookup.)*

**Прапор:** `UR{Hewlett Packard}`

## Task 3: Алгоритм кодування даних

**Мета:** визначити, чим кодувались дані перед відправкою через DNS.

Вкрадені дані ховались не в самому DNS-трафіку взагалі, а конкретно в **імені запиту** (`dns.qry.name`) — саме туди атакуючий підставляв закодовані шматки даних замість реального піддомену. Витягнуто ці імена для пакетів, що йшли на підозрілий IP:

```bash
tshark -r exfil.pcap -Y "ip.dst==22.50.109.94 && dns" -T fields -e dns.qry.name
```

Приклад отриманих рядків:
```
Ci9ldGMvc2hhZG93CmRhdmlkOiR5JG.yeutoube.xyz
o5VCQyQVRzWEZHeG9hM0U2SGJUcXE3.yeutoube.xyz
...
```

**Аналіз:** частина до домену (`yeutoube.xyz` — фейковий/підставний домен, замаскований під легітимний) складається з символів `A-Za-z0-9` і в останньому пакеті закінчується `==` — це padding, характерний саме для **Base64**. Якби це був Base32, алфавіт був би вужчим (`A-Z2-7`), якби Hex — тільки `0-9a-f`.

**Прапор:** `UR{Base64}`

## Task 4: Який файл вкрадено

**Мета:** декодувати дані й визначити вихідний файл.

Важливий нюанс: кожен окремий DNS-запит містить лише **шматок** загального Base64-потоку, розрізаний без прив'язки до вирівнювання (Base64 кодує групами по 4 символи = 3 байти вихідних даних; розрізи можуть падати всередині групи). Тому декодувати можна тільки весь потік одразу, у правильному порядку — інакше кожен окремий шматок буде "битим" Base64.

```bash
tshark -r exfil.pcap -Y "ip.dst==22.50.109.94 && dns" -T fields -e frame.time_relative -e dns.qry.name \
  | sort -n \
  | cut -f2 \
  | sed 's/\.yeutoube\.xyz$//' \
  | tr -d '\n' > /tmp/payload_b64.txt

base64 -d /tmp/payload_b64.txt
```

Пояснення конвеєра (pipeline):
- `-e frame.time_relative -e dns.qry.name` — виводимо два поля: час пакета (для сортування) і саме ім'я запиту.
- `sort -n` — сортування за часовою міткою (перше поле), щоб відновити правильний хронологічний порядок шматків — порядок рядків у виводі tshark сам по собі це не гарантує.
- `cut -f2` — залишаємо лише друге поле (саме ім'я запиту, без часу).
- `sed 's/\.yeutoube\.xyz$//'` — прибираємо суфікс домену з кінця кожного рядка, залишається тільки закодована частина.
- `tr -d '\n'` — склеюємо всі рядки в один суцільний рядок без переносів (бо Base64-потік єдиний, розрізаний штучно).
- `base64 -d` — стандартна утиліта декодування Base64.

**Результат декодування:** вміст файлу `/etc/shadow` — стандартного файлу Linux, де зберігаються хешовані паролі користувачів системи (рядки виду `david:$y$j9T$...` — хеш формату yescrypt). Це один з найчутливіших файлів у Linux-системі, тому його витік — це серйозна знахідка.

**Прапор:** `UR{/etc/shadow}`

## Підсумок / чого навчились

- **DNS exfiltration**: як виглядає в трафіку (односторонні "DNS-запити" без відповіді, на нетиповий зовнішній IP, з незвичними/довгими іменами піддоменів).
- Базові прийоми **tshark**: `-z io,phs` (огляд протоколів), `-z conv,*` (хто з ким спілкувався), `-Y` (фільтр), `-T fields -e` (витяг конкретних значень), `-V` (повний розбір пакета).
- Визначення виробника обладнання за **MAC/OUI**.
- Розпізнавання **Base64** за алфавітом і паддінгом (`==`).
- Що фрагментовані дані (розрізані на шматки без вирівнювання) треба **склеювати в правильному порядку перед декодуванням**, а не декодувати частинами.
