# Задача 2: Silent and Fast — рішення покроково

> ⚠️ **Ця задача не вирішена.** Жодна підзадача не має підтвердженої
> платформою ✅ відповіді — нижче лише те, що реально відомо: невдалі
> спроби учасників і одна зафіксована технічна перешкода. Це чернетка для
> продовження, а не готовий розбір.

## Що відомо про артефакт задачі

З термінала учасника видно спробу проаналізувати файл `dump.scap`:

```text
[maksimka@archlinux ~]$ strings dump.scap > result.txt
strings: 'dump.scap': No such file or directory
[maksimka@archlinux ~]$ cat dump.scap
cat: dump.scap: No such file or directory
[maksimka@archlinux ~]$ cd scap
bash: cd: scap: No such file or directory
[maksimka@archlinux ~]$ cd dump.scap
bash: cd: dump.scap: No such file or directory
```

Перед цим у тому самому терміналі стоїть встановлення пакета `binutils`
(містить `strings`, `objdump` тощо) — отже, учасник щойно доставив
інструмент, але **файл `dump.scap` на той момент не лежав у поточній
теці** (жодна з чотирьох спроб — `strings`, `cat`, `cd scap`, `cd
dump.scap` — не знайшла нічого).

### Практичний урок (навіть без вирішеної задачі)

Перш ніж підозрювати "інструмент не працює" — перевір **найпростіше**:

```bash
pwd          # де я взагалі?
ls -la       # чи файл тут?
find / -iname "*.scap*" 2>/dev/null   # чи він десь в іншому місці?
```

Схоже, файл або лежав в іншій теці (наприклад, `~/Downloads`), або ще не
був розпакований з архіву, або назва відрізнялась від `dump.scap`
(регістр, розширення). Це стандартна помилка на змаганні — перевіряти
шлях і назву файлу займає секунди, а бездумний перебір команд — хвилини.

## Гіпотеза щодо формату файлу — TODO перевірити

Розширення `.scap` найімовірніше вказує на **Sysdig capture** — формат
запису системних викликів у Linux (процеси, мережеві з'єднання, файлові
операції, аргументи команд). Якщо це так, `strings`/`cat` дадуть лише
уривки бінарних даних — потрібен саме `sysdig`:

```bash
# встановити (Arch): sudo pacman -S sysdig
# встановити (Debian/Ubuntu): sudo apt install sysdig

sysdig -r dump.scap                       # прочитати весь capture
sysdig -r dump.scap "evt.type=execve"     # тільки запущені команди
sysdig -r dump.scap "fd.type=ipv4"        # тільки мережеві події
```

Якби гіпотеза підтвердилась, це напряму відповідало б на кілька підзадач:
- `evt.type=accept` / мережеві події → сервіс/протокол доступу (№1), IP і час першого з'єднання (№2, №3)
- `evt.type=execve` → перша команда після входу (№6)
- `proc.name=sshd` + auth-логіка → кількість невдалих/вдалих логінів (№4, №5)
- аргументи команд у `execve` → налаштування persistence (№8), шифрування файлу і passphrase (№9–12)

**Це не перевірено** — TODO для того, хто продовжить цю задачу: підтвердити
формат файлу (`file dump.scap` — перший крок, який тут ще ніхто не робив),
і якщо це справді Sysdig — пройти по підзадачах через фільтри вище.

**Підказка з flag format підзадачі 9:** `UR{file.mp3}` (а не generic
`filename`, як в інших питаннях цієї задачі) — ймовірно, зашифрований файл
насправді **mp3**, тож шукай у capture щось на кшталт `open`/`write` з
розширенням `.mp3` в аргументах, а не намагайся вгадати з нуля. Підзадача 10
(`UR{flag}`) означає, що розшифрований вміст файлу — це вже прямо готовий
прапор у форматі `UR{...}`, тобто мета — не "прочитати аудіо", а знайти
текстовий рядок, захований у файлі з mp3-розширенням (стеганографія чи
просто перейменований текстовий файл).

## Підзадачі — статус спроб

| # | Питання (коротко) | Спроби | Що пробували | Результат |
|---|---|---|---|---|
| 1 | Сервіс/протокол доступу | 0/5 | — | не спробовано |
| 2 | IP зловмисника | 1/5 | `192.168.178.126` | ❌ |
| 3 | UTC час першого з'єднання | 4/5 | `22:31:13` (та ще одна спроба) | ❌ |
| 4 | Кількість невдалих логінів | 0/5 | — | не спробовано |
| 5 | Кількість успішних логінів | 0/5 | — | не спробовано |
| 6 | Перша команда після входу | 0/5 | — | не спробовано |
| 7 | Версія ядра | 0/5 | — | не спробовано |
| 8 | Callback host/IP для persistence | 1/5 | `192.168.178.108` | ❌ |
| 9 | Який файл зашифровано (`UR{file.mp3}`) | 0/5 | — | не спробовано |
| 10 | Вміст цього файлу (`UR{flag}`) | 0/5 | — | не спробовано |
| 11 | Passphrase шифрування | 4/5 | `random/uuid` | ❌ |
| 12 | Base64 flag, перша частина до `//` | 1/5 | `bod` | ❌ (схоже на занадто коротку спробу) |
| 13 | UTC час закриття з'єднання | 4/5 | `19:31:44`, потім `19:31:29` | ❌ обидва |

**Цінне спостереження:** для підзадачі 13 обидві невдалі спроби (`19:31:44`
і `19:31:29`) — в межах однієї хвилини. Це натякає, що загальний підхід
(знайти правильну подію в capture) вірний, але або секунди зчитані
неправильно, або взято не ту саму подію "закриття з'єднання" (наприклад,
останній пакет замість `close()`/`FIN`/timeout).
